# RelayLink v0.1.0-rc.11

这是在 v0.1.0-rc.10 之后收紧管理面、运行时连接限制与密钥文件权限的候选版本。管理入口仍为明文 HTTP，示例与 Docker 默认只监听回环地址；客户端连接上限可立即生效，双向沉默的 TCP 连接按服务端空闲超时关闭。

## 主要更新

- 示例配置与 Docker 将 dashboard.listenAddress 绑定到 127.0.0.1。管理监听不是回环地址时写入 SECURITY 错误日志并输出到标准错误，进程仍会启动。推荐访问方式仍是在服务器本机运行 Agent，再经端到端加密互访打开 127.0.0.1 上的管理页；本候选不新增强制的管理面 HTTPS。
- 登录密码超过 1024 个 UTF-8 字节时在 PBKDF2 之前拒绝。用户名错误仍执行 PBKDF2。同一来源五次失败后锁定该来源，退避从 1 秒起、最长 15 分钟；锁过期后只放行一次进行中的重试，失败次数继续累计。失败记录最多保留 1 万个来源，清理时保留未过期历史；未过期记录占满时拒绝新来源。
- 登录成功的审计事件落库之后才替换进程内已有的登录会话。审计写入失败时登录返回 503，原会话保持有效。
- 密钥尚未校验通过时，ClientNotFound、ClientDisabled 和 InvalidSecret 在线路上统一为 AuthenticationFailed。具体原因仍写入审计和服务端日志；密钥校验之后的失败原因保持原样。
- 每条管理响应设置 Content-Security-Policy（含 frame-ancestors 'none'）、X-Content-Type-Options: nosniff 和 X-Frame-Options: DENY。/api 保持 Cache-Control: no-store。
- 客户端 maxConnections 与 maxPendingConnections 立即生效。降低上限后不再分配新名额，已持有许可的连接保持到结束，释放也不会超过新上限。保存客户端上限后会把配置快照推送给已就绪的 Agent。
- 更新通道或客户端时先写入 JSON，再切换监听和内存配置。绑定失败则写回先前文件，已有连接保持。客户端目录无法接受临时文件时，在改动监听之前失败。删除客户端先删文件，监听更新失败时恢复该文件。
- limits.tcpIdleTimeoutSeconds 在普通 TCP 代理或授权互访双向沉默达到该时长后取消连接并释放名额。省略时为 900 秒，设为 0 表示不因空闲关闭。已接受的 TCP 套接字启用 keepalive，管理概览显示当前值。控制与数据接入在等待未认证握手名额时被取消，或名额已满，都会释放已接受的套接字。RegisterAccepted 携带 halfCloseDrainTimeoutSeconds 与 tcpIdleTimeoutSeconds；当前 Agent 将其用于普通 TCP 中继以及加密或明文互访复制，包括半关闭排空。旧对端忽略新字段。数值跟随 server.json，在下次注册时生效。
- 客户端 JSON、重写后的 server.json 以及 SQLite 审计和流量文件仅服务账户可读：Unix 为 0600，为其创建的数据库目录为 0700，Windows 使用去掉继承的当前进程身份专用 DACL。组或其他用户可读的密钥、私钥、客户端目录或数据库会在日志和标准错误中记 SECURITY。其他用户可写的共享数据库目录、进程临时目录、/tmp、文件系统根以及已有的其他用户可写目录会被拒绝，并要求改用仅供 RelayLink 使用的目录。专用数据库目录会收紧，使随后生成的 WAL 与 SHM 不对其他用户可读；共享父目录不会被改写。systemd 单元设置 UMask=0077。Linux 部署说明与 Agent 文档一致：/etc/relaylink 与 clients 为 0700，密钥文件为 0600。
- CI、发行和 Pages 工作流中的第三方 GitHub Actions 钉到提交 SHA，注释中保留对应版本标签。
- 根 README 不再把 HTTP 设计写成尚未实现。HTTP 设计保持 Draft，并说明 v5 路径已在 main，评估与未测量容量章节仍是草案。Linux 与 Windows 部署说明不再要求 Server 与 Agent 同时升级，改为按 v3 TCP、v4 UDP、v5 HTTP 指向 UDP 与 HTTP 运维说明。

## 升级与兼容性

- NTP1 仍为 v5，JSON schemaVersion 仍为 1。Server 继续同时接受 v3/v4/v5。
- 管理面按设计仍在回环地址上使用明文 HTTP。
- 升级前确认密钥路径和数据库目录满足新的权限检查。Windows Docker Desktop 的绑定挂载可能需要在 Linux 虚拟机内显式执行 chmod 0700 与 0600。省略 tcpIdleTimeoutSeconds 时现在默认为 900 秒；设为 0 可保持此前不因应用层空闲关闭的行为。
- 除此以外，普通 TCP/UDP 与 HTTP 代理行为与 v0.1.0-rc.10 相同。

## 验证与限制

- 已合并的 #3（890a282）、#4（d9e03b8）和 #2（e5834f5）在 Ubuntu、Windows 与 macOS（Intel 及 Apple Silicon）上 CI 通过。
- 在 TestClient-01（Windows，Docker Desktop 29.5.3）上对 e5834f5 做了实机 Docker 冒烟：/health/ready 与 /health/live 返回 200；管理页返回 200，并带有 CSP、X-Frame-Options 与 nosniff；容器内管理监听为 127.0.0.1:18080。Docker Desktop 的 network_mode: host 是 Linux 虚拟机的主机网络，不是 Windows 本机回环；该结论通过 host 网络侧车核对。
- Windows Desktop 上的已知摩擦：首次 compose 启动需要交互输入管理密码；绑定挂载的权限需要在虚拟机内 chmod。本次未做 multipass 或远程测试服务器验收。
- Windows 安装包未签名，macOS 包未签名或公证，与 v0.1.0-rc.10 相同。
