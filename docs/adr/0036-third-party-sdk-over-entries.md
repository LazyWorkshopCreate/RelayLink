# ADR-0036：第三方 SDK 只面向入口，不开放中继协议

文档 ID：ADR-0036\
状态：Proposed\
日期：2026-11-05\
依据：用户于 2026-11-05 要求“供第三方应用集成的 sdk、支持主流平台和开发语言”，并确认 SDK 以数据面为主、有限提供客户端注册与通道注册及访问通道申请，审批仍在管理平台完成。

## 背景

第三方应用要经 RelayLink 访问内网服务，眼下只有一条可行路径：自己算出入口地址再连一个 TCP 端口。授权互访的入口是访问方 Agent 在本机 `127.0.0.1` 选定的端口，普通代理入口是服务端业务监听；两者都没有可供程序发现的稳定契约，Agent 端口在冲突时还会轮换。结果是第三方应用只能靠人工抄地址，把“隧道形态”写死进自己的配置文件。

有两条看起来更“彻底”的方案，都需要先排除：

- 让 SDK 实现 `NTP1` 帧并直连服务端控制/数据端口。这要求第三方应用持客户端密钥、参与会话与绑定令牌协商，等于把中继协议变成对外接口。既有设计中 `NTP1` 明确是内部线格式，持续随能力演进（当前 v5，历史兼容 v3–v4），冻结它对外承诺会立刻锁死演进空间，也会把客户端密钥分发面扩大到任意第三方。
- 让 SDK 内嵌一个 Agent。这会让第三方进程承担身份固定、内层 TLS、访问证明、端口分配与配置快照校验，且与“Agent 是受管主机上的服务”的部署模型冲突。

数据面之外，用户还要求有限的注册与申请能力。这部分属于服务端配置变更，必须走与 AI 自动化相同的批准模型；如果 SDK 自己实现一套配对与令牌，就会出现两套审批入口。

## 决定

1. SDK 不实现中继协议，不做多路复用、打洞或 VPN。它面向“入口”：授权互访是访问方 Agent 的 loopback 端口，普通代理是服务端业务监听地址。
2. 入口发现优先读取本机 Agent 的既有 v2 只读 API（`/api/v2/status`、`/api/v2/channels`、`/api/v2/mappings`），只接受 `127.0.0.1`。Agent 离线、列表为空或多 profile 无法消歧时返回明确错误，不猜测地址。显式配置优先于自动发现。
3. SDK 不持有任何中继密钥：客户端密钥、通道访问密钥、绑定令牌、凭据明文都不进入 SDK 进程。数据面加密强度由通道配置决定，SDK 不得关闭或降级授权互访的内层 TLS。
4. 有限管理面只调用 [ADR-0035](0035-ai-automation-over-peer-channel.md) 的自动化 API，不新增第二套鉴权。只实现三个动作：注册客户端、注册通道、申请访问通道，三者都是需要人工批准的变更申请。**首期只有 C#/.NET SDK 具备完整管理面**；其余语言受“仅标准库/JDK/内置模块”的依赖约束，读不了操作系统凭据库、也需自行实现设备签名，因此首期只交付数据面，管理面扩展须另立 ADR。批准后不向任何语言返回客户端密钥。
5. 配对由 CLI 完成，SDK 读取同一 profile 的凭据；各语言不重复实现配对与证明逻辑。这条在首期实际只对 C#/.NET 成立，其余语言的管理面延后，数据面不需要配对。
6. 契约以仓库内 `contract/`（OpenAPI + 一致性用例）为单一来源。管理面客户端由契约生成，数据面手写。OpenAPI 生成器产不出设备签名证明这一点必须记住：契约只约束形状，证明逻辑仍需手写并纳入一致性用例。
7. 语言基线：C#/.NET、Java 17、Python 3.9、TypeScript/Node 20、Go 1.22、Rust 1.75；平台基线 Windows 10/Server 2019 以上、主流 Linux（glibc 与 musl 分别说明）、macOS 12 以上，移动端不在范围内。优先零原生扩展、最小依赖。
8. SDK 版本独立于文档版本、`schemaVersion` 与线协议版本，并声明支持的自动化 API 版本区间。

## 备选

- **SDK 实现 `NTP1` 并直连服务端**：拒绝。会把内部线格式冻结为对外契约，把客户端密钥分发面扩大到任意第三方，且每次协议演进都成为破坏性变更。
- **SDK 内嵌 Agent**：拒绝。让第三方进程承担身份、TLS、证明与端口分配，与“Agent 是受管主机服务”的模型冲突。
- **SDK 自己实现配对与令牌**：拒绝。会产生两套审批入口，且每种语言都要重写设备证明和证书固定，出错面随语言数倍增。
- **SDK 自动管理连接池与重连**：拒绝。通道有连接上限与撤销语义，隐藏重试会造成配额冲突与难以诊断的“半可用”状态；由应用显式决定。
- **只做 .NET SDK，其余语言给 HTTP 示例**：拒绝。用户明确要求覆盖主流语言；且数据面本身很薄（socket 语义），语言覆盖成本可控，反而管理面才是复用重点。因此数据面六语言齐备、管理面首期只做 .NET，是这个取舍的落点。

## 后果

- 第三方应用必须在能访问入口的主机上运行，或由部署方自行解决入口可达性（例如通过授权互访把入口放在应用所在主机）。SDK 不承担跨网可达。
- SDK 的能力上限就是“连一个地址”，因此它不能替代 RelayLink 的任何安全功能；文档与 README 都必须明确这一点，避免第三方误以为接入 SDK 就获得隧道级保护。
- 入口发现依赖 Agent 本机 API，等于把该 API 从“运维可读”升级为“被 SDK 依赖的稳定契约”。既有 v1/v2 端点形状因此不能在主版本内破坏，需要写入兼容承诺。
- 管理面让第三方能在获批后自助注册客户端与通道，减少管理员手工操作，但审批仍在管理页面；管理员需要建立“一次批准意味着什么”的操作规范。首期只有 .NET 具备管理面，其余语言的使用者需借助 CLI。
- 各语言实现需要一套共享的一致性用例，否则会出现“字段对得上但语义不一致”的问题。CI 必须跑全部语言，不能只跑参考实现。当前流水线只有 .NET 与 Node 工具链，Java/Go/Rust 与 musl、arm64 的 runner 供给需要在实现阶段一并规划，不能先立承诺再补工具链。
- 不修改 `NTP1` 帧与协议版本，旧 Agent 与新 SDK 组合行为不变。
