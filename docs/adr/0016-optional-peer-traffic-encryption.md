# ADR-0016：互访业务流加密按通道可选

状态：Accepted\
日期：2026-09-22

## 背景

原互访设计强制在两端 Agent 之间建立内层 TLS。新需求允许管理员在创建“仅客户端互访”通道时关闭业务流加密，并要求关闭后直接复制流量。这个选择改变了服务端能否看到业务内容，不能复用一个模糊的全局开关，也不能同时取消互访授权。

## 决定

在目标通道增加 `endToEndEncryptionEnabled`，缺失和新建默认值均为 `true`，仅对 `authorizedClientsOnly=true` 的通道生效。服务端按每次请求时的目标通道配置，把模式同时写入 `PeerOpen` 和 `PeerOpenGranted`；目标 Agent 还会与自己的已确认快照交叉检查。模式进入配置摘要和访问证明的域分隔上下文，修改通道会沿用既有规则撤销连接。

加密模式维持内层 `SslStream`、证书指纹固定和 TLS 内挑战证明。明文模式跳过 `SslStream`，但仍在帧化数据流上完成随机挑战和 HMAC-SHA256 访问证明，成功后才连接目标并直接复制业务字节；`Fin` 表示本机 TCP 的单向 EOF。控制连接 TLS、客户端认证、映射授权、一次性绑定令牌、配额、超时、审计及撤销规则在两种模式下完全相同。

线协议版本从 2 升为 3。旧版本没有模式字段，不能可靠区分两端行为；显式拒绝版本不一致优于把 TLS 记录误当明文或把明文误交给 TLS 解析器。

## 备选

- 全局关闭互访加密：无法按通道表达不同安全等级，拒绝。
- 关闭加密时同时取消访问密钥证明：会把 loopback 入口和映射授权错误地等同于目标侧认证，拒绝。
- 在明文业务前继续完成 TLS 握手再退出 TLS：业务并非真正直接复制，且容易产生降级和流边界问题，拒绝。
- 保持强制加密：不满足本次明确需求。

## 后果

明文互访不再具有 RelayLink 提供的业务机密性和完整性；服务端及能观察或控制数据链路的一方可以读取或篡改业务内容。部署方必须仅在受信隔离网络中使用，或确保业务协议自身已经提供端到端加密和认证。现有数据库/API 中历史字段名 `peerCiphertext*` 为兼容保留，在明文通道上实际表示互访数据帧载荷字节；管理页面统一称为“互访转发字节”，并按通道模式说明其为密文或明文。

目标证书身份仍按客户端生成和登记，供该客户端的加密通道使用；明文连接不执行证书校验，但仍受服务端已认证目标会话和访问密钥证明约束。Server 与所有 Agent 必须同步升级到协议版本 3。
