## 1. 范围与现状

本文描述同一 Agent 进程连接多个互不协作的服务端的拟议实现。当前已加入新格式校验、独立配置转换器、服务端单项新格式下载，以及按 `profileId` 启动控制会话和分组的本机 v2 API。主程序仅接受新格式；身份和端口状态读取 `state/<profileId>/`。Linux、macOS 和 Windows 安装包“仅更新”的启动链已接入转换器。本机页面支持动态增删和写请求来源及 CSRF 校验；进程级端口分配与资源隔离已有自动化测试，Windows 安装包三种模式已有隔离环境实测。完整验收记录仍须核对。服务端认证、下发快照、普通转发及互访线协议保持现有语义；一个服务端仍只管理自己创建的客户端、通道和访问映射。

## 2. 本机配置与身份边界

Agent 新配置顶层设置 `dashboardPort`、`outboundPortRangeStart`、`outboundPortRangeEnd` 和 Agent 全局资源上限；`servers` 为数组，允许为空，以便删除最后一项后仍可打开本机页面。每项包含稳定的 `profileId`、`serverHost`、`serverPort`、`dataPort`、`useTls`、`clientId`、`secret`、`trustedCaPemBase64` 与 `reconnect`。连接端点、TLS 信任和重连参数仅对本项生效。`profileId` 使用与客户端 ID 相同的受限字符集，在本机唯一；它不是远端颁发的身份，也不随 DNS 或地址调整而改变。示意结构如下，占位密钥不可运行：

```json
{
  "dashboardPort": 18081,
  "outboundPortRangeStart": 20000,
  "outboundPortRangeEnd": 59999,
  "maxConnections": 2000,
  "servers": [
    {
      "profileId": "east",
      "enabled": true,
      "serverHost": "east.example.com",
      "serverPort": 7443,
      "dataPort": 7444,
      "useTls": true,
      "clientId": "agent-01",
      "secret": "REPLACE_WITH_EAST_CLIENT_SECRET",
      "trustedCaPemBase64": "REPLACE_WITH_EAST_CA_PEM_BASE64",
      "maxConnections": 100,
      "maxPendingConnections": 20,
      "reconnect": { "initialDelaySeconds": 1, "maxDelaySeconds": 30, "permanentErrorDelaySeconds": 60 }
    },
    {
      "profileId": "west",
      "enabled": true,
      "serverHost": "west.example.com",
      "serverPort": 7443,
      "dataPort": 7444,
      "useTls": true,
      "clientId": "agent-01",
      "secret": "REPLACE_WITH_WEST_CLIENT_SECRET",
      "trustedCaPemBase64": "REPLACE_WITH_WEST_CA_PEM_BASE64",
      "maxConnections": 100,
      "maxPendingConnections": 20,
      "reconnect": { "initialDelaySeconds": 1, "maxDelaySeconds": 30, "permanentErrorDelaySeconds": 60 }
    }
  ]
}
```

可提交的脱敏 JSON 已放入 [配置示例目录](../../config/examples/agent.example.json)；本节说明拟议结构。`--check-config` 须一次校验全部配置项：未知或重复字段、重复 `profileId`、无效端口和 CA、密钥占位值或强度不足、配额无效、配置项配额总和超过进程总配额，都使配置检查失败。控制 TLS 的 CA 只验证对应服务端，不使用另一配置项或系统信任库回退。新格式不允许顶层单服务端字段混用，也不允许本地 `channels`、访问映射或访问密钥。新版服务端下载 JSON 使用同一新格式，`servers[]` 只含该服务端的一项，默认 `profileId=primary`；本机页面导入时由管理员确认或调整本机唯一的 `profileId`，不会把下载文件整体覆盖已有配置。服务端管理 API 不接触其他服务端凭据。

每项配置可选 `enabled`，缺省为 `true`，使既有配置和服务端下载文件继续连接；显式为 `false` 时保留注册信息、密钥及 `state/<profileId>/`，Agent 启动后不建立该项控制会话。即使停用，也继续校验该项的端点、密钥、CA 和配额。权威示例中的 `enabled` 见[Agent 配置示例](../../config/examples/agent.example.json)。

## 3. 运行上下文与协议

Agent 为每个 `profileId` 创建一个 `ServerContext`，包含本项只读连接设置、私有 CA、端到端身份、控制会话、已确认快照、心跳和重连状态、Pending/Active 连接注册表、端口映射状态、配额与取消令牌。全进程只共享本机 HTTP 监听、loopback 端口分配器和进程级资源管理。异步任务由各自上下文监督；某项会话异常只取消本项子任务，不能传播到进程级停止令牌。进程停止时统一取消所有上下文并等待清理完成。

注册帧及 `ConfigUpdate`、`ConfigAck`、`Open`、`Bind`、互访消息的线格式不变。每个 TCP 连接从创建时就绑定一个 `ServerContext`；数据拨号使用其 `serverHost`/`dataPort`，令牌仅在该服务端的当前控制会话中使用。进程内查找通道、映射、连接和状态时统一使用 `(profileId, 原有ID)`，不能只用原有 ID。服务器传来的引用只能在同一上下文已确认的快照中解析；两个服务端即使使用相同 ID，也不能跨上下文找目标。互访访问方和目标方必须属于同一服务端的认证会话；本机同时注册其他服务端不提供桥接路径。

每项独立验证配置摘要并原子替换自己的快照。收到无效快照时拒绝该项更新或会话，保留其他项；控制断线时清空该项在线快照，取消该项 Pending、Active 和本机入口，不触碰其他项。每项分别执行心跳、慢速认证重试与网络退避。现有服务端按会话/通道撤销连接的规则仍在各自服务端内执行。

## 4. 端到端身份和本机入口

新格式把状态放入受保护的 `state/<profileId>/`，其中包含该项的端到端身份及端口映射文件。`profileId` 变更视为新配置项，不能静默继承旧状态；端到端指纹变化仍按 [ADR-0011](../adr/0011-client-level-e2e-identity.md) 显式核验和轮换。不同服务端即使 `clientId` 相同，也使用不同证书私钥、信任 CA 和状态文件。旧身份及端口状态由启动前转换器移入首个配置项的新状态目录，主程序不识别旧文件名。服务端下载不包含 Agent 私钥。

端口状态键为 `(profileId, mappingId)`。全进程端口分配器在配置范围内串行保留与绑定 IPv4 loopback 端口，再将成功结果写入对应状态文件；重启优先尝试原端口，被其他配置项或本机进程占用时选择其他端口。只在该项配置版本已确认且实际绑定后，向其服务端报告 `PeerMappingStatus`。单个入口失败仅清理该入口；同一服务端的其他入口和其他服务端入口继续运行。停止或断线只释放该项拥有的监听。

## 5. 配额与故障隔离

每项默认 `maxConnections=100`、`maxPendingConnections=20`，可显式调整；进程级默认 `maxConnections=2000`。配置检查要求各项最大值之和不超过进程总额度，Pending 上限不超过本项总额度。每项先获取自己的额度，再申请本项缓冲和任务；释放使用一次性租约。进程总额度只作为防止错误配置的上界，正常运行时某项无法占用其他项的预留额度。控制发送队列、单连接缓冲和目标拨号任务仍保持有界；一个服务端持续推送或慢读不能建立无限工作队列。共享 CPU、磁盘、网络出口与操作系统句柄仍可能形成主机级瓶颈，运行时应按配置项记录限额拒绝与资源占用，不能承诺主机故障下的独立性。

日志和诊断事件包含 `profileId`、对应的 `clientId` 和必要的会话/连接 ID；不得记录任一配置项的密钥、令牌、CA 正文、证书私钥或业务载荷。对于单项认证拒绝、无效更新、端口冲突、服务端断网与目标故障，应分别报告本项错误并继续监督其他项。

## 6. 本机监控页面与管理 API

本机监控页采用独立的 `RelayLink.AgentWeb` React/TypeScript/Vite 项目，Agent 构建和发布时将静态资源复制到程序目录的 `wwwroot/`，由同一个仅绑定 loopback 的 Kestrel 实例托管。页面通过现有 v2 API 获取分组状态及管理会话；Agent 后端不再拼接多服务端页面 HTML 和脚本。视觉组件与服务端管理页保持一致，构建与部署边界分别独立；架构决定见 [ADR-0021](../adr/0021-standalone-agent-web.md)。

本机监控页按 `profileId` 分组显示各项在线状态、客户端 ID、通道和已实际绑定的互访入口，提供“新增服务端”“导入修改”“停用/启用”和“删除”操作。新增和修改只接收服务端下载的单服务端新格式 JSON；页面不提供逐项输入或编辑连接参数。新增时根据下载项的 `profileId` 自动选取本机唯一标识（冲突时追加数字后缀）；修改时选择已有项并保留该项本机 `profileId`。页面只预览非敏感字段，提交成功、失败或关闭弹窗后清空导入的密钥。已保存项不提供密钥预填、显示、复制或下载。删除前明确提示本机连接会中断、远端客户端记录和密钥仍由远端管理员处理。删除最后一项后页面显示空状态和新增入口。

新增只允许尚不存在的 `profileId`；若同名受保护状态曾被删除项保留，页面须提示并要求确认仍关联原服务端身份，不能静默复用。修改只能使用明确的导入操作，且导入文件的 `clientId` 必须匹配原有客户端身份；如需更换客户端身份，应新增独立配置项并在远端核验新身份。新增或修改前校验完整项及整体配额、CA 和密钥；保存成功后创建或重启已启用项的上下文。目标服务端暂时不可达不使保存回滚，该项保持离线并独立重试。删除先原子保存移除后的配置，再取消该项会话及连接并释放入口；API 等待该项停止、资源释放完成后才返回成功。保存失败时运行状态和旧配置均不改变。写操作按配置版本串行化；请求携带当前版本，过期版本返回冲突，避免两个页面互相覆盖。所有变更按同一目录中的受限临时文件、校验、刷新落盘与原子替换写入，不产生包含密钥的日志或公开备份。仅页面写操作触发运行时变更；管理员直接修改文件仍需重启 Agent。

新增匿名 GET `/api/v2/status`、`/api/v2/channels`、`/api/v2/mappings`，每个响应以 `servers[]` 分组；每组含 `profileId`、`serverHost`、`useTls`、`clientId`、`online`、`updatedAtUtc` 及对应资源列表。离线组仍显示身份和离线状态，资源列表为空，不把旧地址标为可用。写接口为 `POST /api/v2/admin/servers`、`PUT /api/v2/admin/servers/{profileId}` 与 `DELETE /api/v2/admin/servers/{profileId}`；要求先取得本机页面会话及 CSRF 令牌，无需管理密码。修改须匹配原有 `profileId` 与 `clientId`，先校验完整配置并持久化，再停止旧上下文并按启停状态决定是否启动新上下文；沿用原端到端身份和本机端口状态。所有 GET 均使用白名单 DTO，任何接口均不返回已保存的 `secret`、CA 正文、私钥或访问密钥；写接口的请求正文和验证错误也不得记入日志。旧只读查询依然匿名；本机 HTTP 只绑定 `127.0.0.1`，全部响应 `Cache-Control: no-store`，不启用 CORS，限制请求体大小并拒绝跨站来源。管理页及表单使用限制外部脚本的 CSP。

本机页面首次读取会话 API 时取得短期 HttpOnly、SameSite=Strict Cookie 与 CSRF 令牌；写请求同时校验 Host、Origin、Cookie 和 CSRF 令牌。无需管理密码或登录。注册密钥仅在导入与提交期间进入浏览器内存和请求，保存后只存在于受保护配置与 Agent 进程内存，不进入页面读取响应。loopback 可被本机其他进程访问，配置文件依赖操作系统权限保护；来源和 CSRF 校验用于防止其他网页伪造本机写请求。

现有 `/api/v1/*` 与 `/api/status` 在仅有一个配置项时保留现有响应形状；多个配置项时返回 `409 Conflict` 和不含敏感信息的 v2 路径提示，不任意选择一个服务端冒充全局状态。`dashboardPort=0` 仍同时关闭页面与 API。服务端各自的管理页面和状态 API 不变，只显示本服务端的会话与入口报告。页面增删改只修改已经采用新格式的配置，不负责旧格式转换。

本机页面单独显示“已停用”，与网络原因的“离线”区分；停用和启用无需导入 JSON。`PUT /api/v2/admin/servers/{profileId}/enabled` 携带配置版本及目标布尔状态，沿用写会话、同源及 CSRF 校验。停用先持久化状态，再停止该项控制会话、活动连接、重连和本机入口；待资源释放后返回。重新启用先持久化，再启动该项会话，并沿用原端到端身份和端口状态。两项操作不重启其他服务端；保存失败不改变运行时状态。导入修改保留当前 `enabled`，不会因下载 JSON 中的值将停用项重新启用。v2 分组状态响应新增 `enabled` 字段；停用时 `online=false`，通道与入口列表为空。架构取舍见 [ADR-0023](../adr/0023-persistent-agent-profile-disable.md)。

## 7. 已有 Agent 升级与配置转换

提供独立的 `RelayLink.Agent.ConfigMigrator` 转换器。它接受 Agent 配置路径，在 Agent 进程启动前执行；旧单服务端 JSON 转换为只含一个 `servers[]` 项的新格式，为旧项指定稳定的 `profileId`（默认 `primary`），补全旧格式中缺省的有效端口和本机参数，并保留原 `clientId`、`secret`、连接端点及 TLS 信任语义。若旧配置使用 `trustedCaPemPath`，转换器读取并验证原 CA 公钥证书后写成该项的 `trustedCaPemBase64`；主程序不解析旧路径字段。已安装的旧 Agent 升级时，转换器还把 `<clientId>.e2e.pfx` 和 `<clientId>.ports.json` 的内容迁入受保护的 `state/primary/`，校验证书指纹与端口状态一致，主程序此后只按 `profileId` 读取新路径。原配置和旧状态文件作为受保护的回退材料保留，不作为运行时输入；不得把同一私钥关联到第二个服务端。

转换器先严格校验旧输入并在同一受保护目录准备新状态文件；状态文件写入完成、权限收紧并校验后，才以受限临时文件原子替换配置。配置替换是提交点：在此之前失败或崩溃，旧配置及状态仍可供重试，未完成的新状态不得被 Agent 使用；在此之后，新配置引用的状态文件必须已经完整。重试时验证已准备文件与旧源一致，不覆盖不一致的现有状态。新格式输入直接校验并退出成功，不再次转换、生成身份或触碰配置；转换失败则返回非零并停止启动链，不把旧格式交给新 Agent 尝试读取。错误中不包含密钥、CA 正文或私钥。旧文件的最终清理是单独的显式运维操作。

所有交付入口都须保证“转换器成功 → Agent 启动”：Windows 安装器的“仅更新”在停止旧服务、替换程序后运行转换器，成功才重启服务；Linux systemd 使用 `ExecStartPre`；macOS launchd 使用先运行转换器再 `exec` Agent 的启动包装脚本；控制台启动与手工部署也先执行转换命令。后续重启仍先运行转换器，但新格式仅作只读校验。若绕过交付入口直接以旧配置启动新 Agent，主程序须清晰报错并退出，不能在配置加载器、会话或页面中做隐式兼容。Linux/macOS 服务包升级只替换程序目录并保留状态目录。

新版 Windows 安装包的“首次安装”和“重新配置”只接受新格式输入，完整校验后才写入受保护的运行配置位置；旧格式输入在清理原安装状态之前就应明确拒绝。新版服务端的受保护下载接口生成单项新格式，供安装包直接使用。旧版服务端下载文件可由独立转换器以“单文件输入→新文件输出”模式预先转换，再提供给安装包；该模式不接触已安装 Agent 的状态，也不由安装包隐式调用。重新配置仍按既有语义清理 Agent 管理的配置和身份，再写入新格式；执行前须提示既有固定指纹和入口端口可能失效，不能当作保留身份的升级路径。新版安装包的这两条路径不会在运行配置位置落下旧格式，启动前转换器对新格式只作校验。

转换器完成后，旧客户端按原密钥和原端到端证书重新注册；升级重启本身会断开旧 TCP 连接，业务须重新建立。服务端已固定指纹不变，端口状态优先复用原本机入口端口。此后页面首次新增服务端只在现有新配置中追加配置项，不触发转换，也不额外中断旧项。删除旧项时移除配置和运行上下文，迁入 `state/primary/` 的身份与端口状态仍受保护地保留；重新使用该 `profileId` 前须确认仍关联原服务端。状态清理不作为删除连接项的副作用。

## 8. 验证与实施顺序

先实现独立转换器、各平台启动前置步骤和只接受新格式的 Agent 配置加载，再拆分控制会话与转发运行上下文，然后加入全局端口分配器、本机 v2 状态及本机管理写接口，最后执行 [A61–A69](../requirements/2026-09-28-multi-server-agent.md#验收标准)。自动化测试已覆盖相同 ID、不同 CA/密钥、有效数据绑定令牌跨服务端被拒、一项停机或错误快照时另一项继续工作、两服务端并发大流及半关闭、单项配额耗尽后的跨项接入、本机页面在线增删及删除最后一项、删除在线项时关闭活动流、写入失败后重试和并发版本冲突、旧状态转换的分阶段中断与重试、旧配置转换后新增第二项并重启，以及同名互访入口预留端口冲突和单项绑定失败后的另一项转发。旧端口状态迁移后已用真实互访连接验证原端口复用；命令行测试已验证旧格式被新 Agent 拒绝，独立转换器单文件输出通过新 Agent 预检。

Windows Sandbox 实测使用新编译安装包和虚构配置：首次安装写入的新格式文件与输入哈希一致，服务运行且配置 ACL 仅允许 LocalService 读取；首次安装和重新配置均在停服清理前拒绝旧格式。重新配置新格式可清理受限 ACL 的旧身份及诊断状态并重启服务；旧版单文件下载经独立转换器生成的新格式也可重新配置。模拟旧版已安装状态后执行“仅更新”，旧配置备份、端到端身份哈希和端口状态保持一致，重复更新仍不变；故意制造旧/新端口状态冲突时安装器返回非零、旧配置与状态保持原样且服务不启动。配额单元测试验证重复释放不重复扣减，集成测试验证饱和连接结束后同项容量恢复；页面、API、错误响应与诊断日志均检查了密钥不泄露，Sandbox 中的安装日志也做了虚构密钥扫描。详细结果见 [多服务端验收记录](../testing/multi-server-agent-verification.md)。本文状态仍为 Draft，不代表架构评审已完成。
