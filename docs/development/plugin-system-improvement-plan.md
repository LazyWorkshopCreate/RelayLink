## 1. 目标与范围

优先修复已经实现的插件路径，使 HTTP/HTTPS 的每次请求、SSH 的目标认证和动作放行、连接生命周期及审计统计能够相互一致。随后修复配置持久化、凭据管理和页面可用性，最后补齐验证记录。

两份报告共提供 19 个 CR 编号和 10 个 IR 编号，存在重合，不能相加当作独立缺陷数量。本方案按根因和交付依赖归并为 W01–W17，保留所有原编号供追踪；调整优先级时以当前代码和复现证据为依据。

2026-10-31 用户明确要求提交本方案并分批实施直至完成测试。本方案范围内 W01–W17 已完成处置，本机完整单元 358 项、包含真实旧端的集成 156 项以及前端/网站检查通过；实施进度和证据见下表及验证记录。2026-11-04 补充复核修复了需求索引与协议参考表未同步，并补齐此前"已验收"声明缺少的回归用例，见 [TST-009 §7](../testing/plugin-system-remediation-verification.md#7-2026-11-04-复核收口)。该授权覆盖本方案限定的修复范围，不等同于批准原插件需求的全部未来能力。关联的 [REQ-001O](../requirements/2026-10-28-plugin-system.md)、[DES-009](../design/plugin-system.md) 保持 Draft，[ADR-0028](../adr/0028-server-inspection-channels.md)、[ADR-0029](../adr/0029-application-plugins-and-bridge.md) 保持 Proposed。

当前修复范围包括两类可审计通道的 HTTP/HTTPS、SSH、已有审批等待逻辑、配置/API、秘密库和状态页面。RDP 门控、完整管理员审批、凭据发放、桥应用、证书与策略编辑表单另列后续能力，不以“审查修复”名义扩大范围。

约束继续有效：保留 `none` 的原始 TCP、UDP、端到端/明文互访和目标 Agent HTTP 反向代理；不加载外部插件、不热更新、不增加远端脚本、不重放业务请求。任何拒绝或故障不得降级为原始复制。

## 2. 两份报告的差异处理

| 差异 | 本方案采用的判断 |
|---|---|
| TST-007 将 SSH 目标主机键列为低风险；IR-02 有陌生主机收到测试口令的复现 | 按 P1 修复。目标 Agent 的腿部 TLS 不能认证 Agent 后方的 SSH 服务；只记录指纹不足以形成校验 |
| TST-007 摘要称整体失败关闭路径完整 | 该结论限于其当时覆盖范围。IR-01 和 IR-03 已复现 HTTP 规则绕过及审计失败后发送命令，不能据此认定插件放行边界完整 |
| CR-02、CR-03 为“高”；IR-09、IR-05 为 P2 | 修复计划按 P2 安排。两者分别是状态误判和策略配置被拒；不将“拒绝加载”写成“悄悄忽略已配置的拒绝策略” |
| CR-04、CR-07 将 RDP/HTTPS 表单视为缺陷；独立报告单列未完成范围 | 分开处理：本轮修复“可保存/可选择却不可用”的入口与提示；RDP 数据面及完整证书表单另行补齐 |
| CR-11 称 key/store 不匹配或解密失败都会阻止启动 | 需缩小结论。[CredentialStore 构造函数](../../src/RelayLink.Server/Runtime/CredentialStore.cs) 只加载/生成 key，未在构造时解密 store。缺失/非法 key、目录创建失败可在启动失败；长度合法但不匹配的 key 或损坏 store 通常在第一次读取时失败。两类故障分别验收 |
| CR-09 建议“先审计后写入” | 不能简单把 `credential_saved/success` 移到写入前，否则磁盘写入失败会留下虚假成功。应区分变更意图、实际应用结果和结果审计状态，见 B5 |
| CR-10 与 CR-01 被分别排序 | 必须与空闲回收、阻塞写、配额一起修。只去掉会话总超时，会暴露空 abort 引起的挂起 |
| CR-14 列出多个缺失事件 | 已有 `peer_connection_closed` / `proxy_connection_closed`，不能写成完全没有关闭审计。区分已实现路径的审计缺口与尚无审批/发放功能导致的事件缺口 |
| CR-16 未观察的拒绝审计异常 | 属于任务管理和诊断缺陷，不据此断言必然放行或进程必然崩溃；与允许决定必须落库分别处理 |

CR-08 的加载时绝对化、CR-09 的先变更后审计、CR-18 的删除未清理均已在当前调用链重新核对。方案初稿阶段未重新执行此前探针；实施阶段将反例迁入正式测试，结果另见验证记录。

### B1：HTTP/HTTPS 逐请求检查

主要位置：[HttpInspection.cs](../../src/RelayLink.Server/Runtime/HttpInspection.cs)、两类通道调用点、HTTP 单元/集成测试。

1. 用能识别完整 HTTP/1.1 消息边界的处理路径替代“首头检查后原样复制”。优先验证能否复用仓库现有虚拟连接宿主模式，在服务端插入逐请求策略；选用成熟 HTTP 处理组件时先验证原有 Host/Origin、流式和升级行为，不沿用手写首包过滤作为安全边界。
2. 对每个请求执行解析、策略、必要等待和允许审计，再转发该请求。首请求拒绝时目标零连接；已复用的连接中后续请求被拒时，不再发送该请求的头或正文，并记录其结果。
3. 正确处理 Content-Length、chunked、请求体、响应边界、临时响应、`Expect: 100-continue`、keep-alive 和 pipeline；歧义或非法消息失败关闭。WebSocket 只在升级请求获准且完成升级后转入字节转发，不宣称检查帧内容；未支持的 CONNECT 等隧道行为明确拒绝。
4. HTTPS 继续终结调用方 TLS，并在向目标发送请求前校验上游 TLS。此改动不移动现有 `applicationProtocol=http` 在目标 Agent 的处理位置。
5. 成功转发的请求头、首批预读正文及后续正文均计量一次。审计不保存查询串、凭据头和正文，不启用隐式业务请求重试。

**验收：** HTTP/HTTPS × server-peer/server-jump 均覆盖“第一请求允许、第二请求拒绝/审批”、流水线跨 read 边界、chunked/正文分段、100/最终响应和 WebSocket 升级。歧义负例包括 Transfer-Encoding/Content-Length 冲突、冲突的重复 Content-Length 和重复 Host，确保策略与目标解释的请求边界及主机一致。被拒请求字节未到达目标，允许请求完整传输；单 GET 的请求字节计数非零且准确。若先采用单请求实现，必须明确限制并在请求边界关闭，不能透传第二请求；该限制须同步文档，不能宣称完整复用支持。

### B2：SSH 安全门槛、配置与 channel 隔离

主要位置：[SshInspection.cs](../../src/RelayLink.Server/Runtime/SshInspection.cs)、[InspectionPolicy.cs](../../src/RelayLink.Server/Configuration/InspectionPolicy.cs)、[ChannelApplication.cs](../../src/RelayLink.Server/Configuration/ChannelApplication.cs)。

1. 建议首期使用管理员配置的目标主机键 SHA-256 指纹；未知或不匹配时关闭，不自动 TOFU。该公有信任信息只在服务端使用，写入配置设计和示例，不下发秘密。校验成功前不向目标发送口令或发起私钥认证；无指纹的存量 SSH inspection 配置仍可加载，但该通道不可用并给出原因，不能默认信任任意键，也不能牵连整个 Server 启动。多键轮换与 SSH CA 可另行设计。
2. 首次目标连接前持久化允许决定；每次 shell/exec/subsystem 请求发送前也必须有对应允许审计。目标认证、开 channel、执行结果分别记录，不能将预先允许写成执行成功。审计失败时阻止新动作并按连接策略清理。
3. 将认证、动作响应和拒绝审计纳入可等待的异步流程；库事件不能等待的任务交由会话拥有者追踪和收尾。消除未观察的 `_ = AuditAsync(...)`；拒绝审计失败仍保持拒绝，并写脱敏诊断。
4. 允许合法 `inspection.ssh`，校验跨应用字段、命令前缀数量/长度和审批期限。当前未真正桥接的 TCP、agent、X11 forwarding 开关设为 `true` 时明确报不支持，不能放行后无行为，也不能静默忽略。命令前缀规则只是 exec 字符串匹配，不承诺 shell 沙箱。现有管理请求 DTO 不接受 `Inspection`，本轮以文件配置生效、既有 API 编辑其他字段时保留并校验策略为范围，不宣称已提供策略写入 API；新增该契约与表单另行安排。
5. 每个 caller channel 拥有独立目标 channel、有限初始化队列及串行状态变更。`pty-req` / `env` 仅作用于所属 channel，消费后清理；`window-change` / `signal` 根据当前状态即时处理，不向以后创建的 channel 重放。限制条数和累计字节；检查自定义处理与 `PipeAsync` 的职责，防止重复或绕过策略。

**验收：** 有效主机键成功，未知键/变更键拒绝且密码发送次数为零；首次决定审计失败时目标零连接，后续动作审计失败时目标 exec 计数不增加；文件加载覆盖 shell/exec/subsystem 和非法 forwarding，既有 API 编辑其他字段后策略保持且继续生效；同一 SSH 连接的两个 channel 使用不同环境/终端信息且互不污染，信号不串用；并发关闭和超限请求没有遗留任务或无界缓存。

### B3：统一生命周期、审批期限和计量基础

主要位置：[PeerRelayRegistry.cs](../../src/RelayLink.Server/Runtime/PeerRelayRegistry.cs)、[ProxyListenerService.cs](../../src/RelayLink.Server/Runtime/ProxyListenerService.cs)、[PeerSessionCoordinator.cs](../../src/RelayLink.Agent/PeerSessionCoordinator.cs)、[ControlSessionWorker.cs](../../src/RelayLink.Agent/ControlSessionWorker.cs)、[RelayPump.cs](../../src/RelayLink.Transport/RelayPump.cs) 及协议消息。

| 阶段 | 期限与资源 | 放行条件 |
|---|---|---|
| 绑定、腿部 TLS、访问证明 | 有界建立期限；持有总连接和 pending 配额 | 认证成功；业务目标仍不连接 |
| 收集策略输入 | 有界 HTTP 头/SSH 前门认证与请求读取期限 | 允许调用方向插件发送输入，不代表目标已放行 |
| 首次审批等待 | 独立审批期限，关联连接撤销；保持 pending | 当前无批准闭环时到期拒绝 |
| 连接目标及上游认证 | 从该阶段开始计算目标连接和应用握手期限 | 允许决定已持久化，目标连接/认证成功 |
| 业务转发 | 取消建立计时器；使用生命周期、空闲和阻塞写期限 | 转 active，释放首次 pending 一次 |
| 半关闭、终止 | 正常 EOF 有界排空；故障立即双向 abort | 观察任务退出，配额、流和审计各自收尾 |

必须按以下顺序实施：

1. 先实现幂等 abort/close：取消共享会话令牌，关闭两侧以解除阻塞，等待并观察两个方向任务。替换 peer HTTP 的空 abort；SSH 的 session、channel 和 pipe 也必须归属同一清理流程。正常 EOF 和故障不能共用立即丢弃尾部数据的处理。
2. 再同步 Server 和 Agent 的阶段期限。当前目标侧 `PeerSessionCoordinator` 用 open+targetConnect 等待放行，`ControlSessionWorker` 用剩余 open 期限等待；只延长 Server 的审批令牌仍会被目标 Agent 提前切断。审批后的目标连接使用新的阶段期限。
3. 区分“可向插件提供输入”和“业务已建立”。调用方当前收到证明后的允许字节即开始发送应用输入；不能简单把该字节推迟到审批完成，否则插件等请求头、Agent 等审批会死锁。后续状态通过有版本/能力约束的控制通知传达，不向已开始的业务流插入新状态字节。
4. 为 peer 路径补足目标就绪/失败确认及路由，校验目标会话和连接归属。现有 `TargetReady/OpenFailed` 主要服务普通 pending registry，不能只复用消息类型而不处理 peer 状态。目标 TCP 就绪后，先在前置审计成功的条件下允许目标腿承载插件握手，服务端才能完成 HTTPS 上游 TLS/SSH 目标认证；不能把 `Start` 或目标侧 pipe 一并推迟到认证完成，否则形成第二种等待死锁。此时仍持有首次 pending，最终认证完成才转业务 active。
5. 保留 [ADR-0013](../adr/0013-sqlite-audit-gate.md) 要求的 BindAccepted/Start 前持久化审计门槛。若新增“建立准备”事件，须明确其与现有 opened 事件的兼容；不能为修正展示而删除前置门槛。业务 active 计数及首次 pending 释放发生在插件放行、目标就绪后；目标失败不能被报告为业务连接成功。
6. 复用实际数据传输观察点，同时更新应用字节和空闲活动；再移除贯穿整场会话的 open 超时。Stream 写入也需独立阻塞期限，`idle=0` 不能让阻塞写无限等待。建议 SSH keepalive 不计作业务活动，该口径需写入设计并测试。
7. 活动连接中的后续 HTTP 请求/SSH channel 审批使用有界操作等待额度，不反复切换整条连接的 active/pending 状态，也不重复计算连接数。

涉及新阶段通知前先核实 v6 的对外交付情况：已交付的线协议不能静默改变等待或帧语义，应增加版本/能力协商；未支持的对端明确拒绝新能力。保留 v3–v5 的既有过滤与回归，不用旧端忽略未知字段充当安全边界。

**验收：**

- 两种模式的 HTTP/HTTPS/SSH 活跃会话跨越 open 期限仍完整传输；原 30 字节/30 秒反例应收到全部正文。
- 采用短测试期限，例如 open=2 秒、approval=5 秒，Server 与目标 Agent 不提前退出；最终原因为 `approval_timeout`，目标零连接。
- 首次 pending 上限 1 时第二条等待连接被拒；审批超时、断线、管理员断开和配置撤销后容量恢复，无负计数或双释放。
- 一侧失败、另一侧持续阻塞时在规定时间结束；半关闭能排空反向尾部，排空超时也能结束。覆盖 idle=0、真正空闲及持续活动三种情况。
- 目标连接失败、上游认证失败和撤销竞态都有准确终态；目标 TCP 已就绪但上游认证延迟/失败时无等待死锁，按期结束且不产生业务成功计数；必要审计在放行前提交，终止事件关联同一连接 ID。

### B4：持久化模型、能力校验与页面可用性

主要位置：[ConfigurationLoader.cs](../../src/RelayLink.Server/Configuration/ConfigurationLoader.cs)、[ChannelConfigurationEditor.cs](../../src/RelayLink.Server/Runtime/ChannelConfigurationEditor.cs)、[ClientConfigurationEditor.cs](../../src/RelayLink.Server/Runtime/ClientConfigurationEditor.cs)、[ChannelAvailability.cs](../../src/RelayLink.Server/Runtime/ChannelAvailability.cs)、AdminWeb。

1. 分离磁盘原始配置和运行时解析结果。保留相对证书路径，解析基准仍为所属客户端配置文件目录；通道编辑、客户端编辑、身份登记等会重写 client 的路径都不得把运行时绝对路径序列化回去。配置目录搬迁后重新解析，不能靠字符串裁剪反推原始路径。
2. 将模式、应用、协议版本、控制 TLS、支持状态作为共用能力检查的输入；文件加载和 API 保存均对 inspection 模式要求控制 TLS。既有 `none` 普通 TCP 保持原要求。
3. server-peer 可用性检查包括两侧就绪和版本、映射和目标启用、目标授权类型、地址已上报及应用已实现；SSH 必需的目标信任材料缺失也应判为未就绪。页面显示的是“入口可接受连接”，不是承诺业务目标认证一定成功；列表刷新不探测目标或解密凭据。
4. 对可审计 RDP，暂禁新建和启用；存量明确标“不支持”，允许停用、删除，继续目标零连接。不要让一个旧 RDP 配置导致整个 Server 无法启动。`none + app:rdp` 标签继续合法。
5. 在缺少证书表单期间，仅禁用 inspection 新建/首次选定中的 HTTPS，并提示通过配置文件提供材料。文件已配置的 HTTPS 保留查看和编辑其他字段能力；普通 HTTPS 标签和现有 HTTP 反代不受影响。服务端错误说明应指出缺少材料，不增加私钥上传能力。
6. 保留前缀按忽略大小写识别，但文件只接受规范小写 `app:ssh/rdp/http/https`，对混合大小写和重复保留值给明确错误；API 应用选择仍规范化写入。避免把此前的自由 tag 静默变成可执行应用，提供人工修正说明并同步规范。前端使用 API 派生 `application`，不另写一套宽松解释。

**验收：** 编辑其他字段后相对证书路径保持不变，复制配置目录后仍能加载；类型不可变、自由 tag 不触发下发及首次选定应用撤销规则保持。覆盖双 v7、单侧旧版/离线、目标停用、无地址、RDP 未支持的状态矩阵；禁止操作不写文件、不撤销无关连接，保留所有 `none` 应用标签及旧 HTTP 类型。

### B5：凭据库变更和生命周期一致性

主要位置：[Program.cs 凭据 API](../../src/RelayLink.Server/Program.cs)、[CredentialStore.cs](../../src/RelayLink.Server/Runtime/CredentialStore.cs)、通道/客户端编辑器、秘密文件权限和运维说明。

**变更响应与审计。** 建议采用“持久化变更意图 → 原子应用秘密库更新 → 记录结果”的流程，统一非秘密操作 ID。预审计失败则不改秘密库；写入失败则报告未应用，不能预写成功。秘密库已经原子替换成功后，即使结果审计失败，也不能返回暗示未应用的普通 503。响应必须准确说明 applied 与审计状态；无响应的重试通过操作 ID 确认结果，删除重试不能被误解释为首次没有成功。

若要求进程崩溃后自动补齐结果审计，建议将最小操作结果元数据与秘密库变更原子写入，再进行有界的审计对账；不要宣称 SQLite 与独立文件具有同一事务。此恢复语义在实施前写入 ADR 和 API 契约，不记录秘密、不重放业务 SQL 或目标操作。至少覆盖变更前、文件替换前后、结果审计和客户端断开各故障点。

**故障范围。** 将秘密库初始化/读取异常转成明确的健康状态。建议遵循当前设计的“可审计通道失败关闭”，使管理诊断和不依赖该库的 `none` 通道仍可启动；不要把不可读库视为空库或自动生成新 key 覆盖。分别测试 key 缺失、格式非法、合法长度但错误、store 损坏、权限拒绝、磁盘写入失败。若选择整个 Server 失败停止，需明确修改设计及部署说明，不能让构造函数偶然决定故障范围。

**删除与重建。** 将凭据写入、通道/客户端删除及重建纳入一致的配置操作协调，消除 `HasChannel` 检查后通道被删除的竞态。建议用可恢复删除标记记录撤销、配置移除和秘密清理进度；清理未完成时拒绝同 ID 重建及新凭据读写，恢复后幂等清理，防止重建复用旧凭据或旧服务端 SSH 主机键。锁顺序固定，不能在失败时悄悄恢复已经删除的秘密。

**验收：** API 返回结果与磁盘事实一致；故障和重试不重复或丢失操作结果；删除单通道、删除整个客户端、同 ID 重建均无旧秘密/主机键继承；清理失败和进程重启有可恢复状态；备份恢复测试成套包含配置、key、store 及操作结果/删除标记等恢复元数据，若后者不在 store 内则须明确列入备份清单，使用测试材料并检查权限。日常口令轮换仍只影响之后的目标认证，不因本轮修复强制断开已认证会话。

### B6：可观测性、回归和文档收口

- 给应用字节定义统一口径，覆盖请求头及正文、SSH channel 数据，不混入腿部 TLS/SSH 传输开销；连接快照、关闭审计和分钟历史来自同一计量来源。保持 `peerCiphertext*` 对旧 `none` 互访的含义，历史追加字段而不改写旧行。
- HTTP 为每个请求记录决策与最终响应状态，SSH 关联认证、channel、命令/子系统、结果和结束；同一传输连接 ID 下增加必要的请求/channel 关联，不只按整条连接合并。审计详情仍有界并脱敏。
- 关闭/结果审计失败按诊断处理，不将已执行动作假装回滚；新请求和新动作的允许决定仍必须成功落库。保留既有审计查询和重启恢复语义，避免新增事件导致重复关闭或重复流量。
- 当前审批等待只记录进入、超时/撤销/拒绝；没有批准 API 时不伪造 granted。`credential_released` 随未来发放功能实现，不为“事件齐全”提前创建无实际含义记录。
- 同步需求 §6、设计文首和能力表、协议/配置说明、脱敏示例、运维故障说明及验证记录。明确“实现了什么、仍有什么缺陷、哪些未实现”，不因代码存在改变 Draft/Proposed 状态。

**出口：** W01–W17 均有处置记录；属于未来能力的部分注明延期和边界，不能以隐藏入口代替功能验收。对每批保存提交 SHA、命令、结果和失败原因；保留首轮失败及重跑信息。
