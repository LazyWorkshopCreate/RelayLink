# 文档管理规则

文档 ID：DEV-002\
状态：Active\
版本：v1.2.0\
更新日期：2026-09-21

## 1. 文件归属与格式

- docs 是持续维护文档的唯一入口，README 只概述并链接，不复制整份设计。
- 正文中文，技术标识保留英文。文件名使用稳定的英文小写短横线形式，如 technical-design.md。
- Markdown 使用 UTF-8 无 BOM、LF。图优先使用 Mermaid；图片等附件放对应文档目录的 assets/，相对链接引用。
- 不以 final、最终版、v2副本等形式复制活动文档。Git 保存历史；文档版本写在元数据中。
- 正式需求、设计和规则文档包含文档 ID、状态、版本、更新日期；调研文档另保留查阅日期。

## 2. 内容边界

- 需求说明做什么、范围和验收；设计说明如何做、取舍、协议和故障处理。
- 运行手册描述已经可执行的操作；尚未实现的命令或模板必须注明规划性质。
- 来源事实、设计建议、已验证结论分别表述。性能数字附测试条件；未实测就写目标。
- 可提交的脱敏 JSON 示例以 [config/examples](../../config/examples/) 为准；设计文档说明字段与行为，避免维护两份可执行示例。
- 禁止真实密钥、私钥、数据库密码、客户配置、SQL 载荷进入文档和截图。

## 3. 状态与评审

- 需求：Draft → Accepted → Done。`Accepted` 表示需求内容已经评审并冻结，不表示实现和验收已经全部完成；只有需求实现及其全部验收均有证据时才标记 `Done`。
- 设计：Draft → Accepted；明确采纳决定后更新状态，不因代码已开始编写自行改为 Accepted。
- ADR：Proposed → Accepted / Rejected；已采纳决定被替代时标记 Superseded 并链接后继 ADR。
- 工作规则使用 Active。状态只描述文档决定，不代表实现进度；实现进度在专门计划或验证状态文档中说明，根 README 仅保留产品介绍和静态信息。
- 用户后续明确指示优先于旧设计；同一变更中更新受影响文档，保留取舍说明。

## 4. 更新与追踪

- 功能、默认值、配置 schema、协议、超时、统计口径或部署行为改变时，同步修改对应需求/设计、示例和测试。
- 引用既有 FR-xx、Axx 编号追踪功能及验收。不要因插入条目重排旧编号；新条目追加稳定编号。
- 仅文字或命名修订可增加补丁版本；兼容性内实质增补增加次版本；破坏性范围变更增加主版本，并说明迁移影响。
- 文档版本、程序版本、schemaVersion、线协议 version 相互独立，不自动同步递增。
- 重命名或移动文档时同步更新所有入链及 docs/README.md。删除内容前检查是否被 ADR、代码或验收引用。
- 变更原因写提交信息或 ADR；不在每份文档尾部堆积重复变更日志，历史以 Git 为准。

## 5. ADR 规则

文件命名 `NNNN-short-topic.md`，顺序编号，至少包含状态、日期、背景、决定、备选、后果及关联文档。适用于传输结构、认证、配置生效、高可用等重要取舍；普通实现细节不强制新增 ADR。

已采纳 ADR 保留历史语义，后续改变通过新 ADR 替代，不能把旧决定改写为从未存在。

## 6. 提交前检查

1. 文件名、元数据、索引、相对链接有效；Markdown 代码围栏闭合。
2. JSON 示例语法有效，命名、字段和默认值与权威配置定义一致。
3. 搜索受影响旧名称和路径，避免搬迁后继续引用失效入口。
4. 不把 Draft 结论、未执行的测试、容量目标写成已经批准或验证的事实。
5. `git diff --check` 通过，并检查暂存文件无真实环境秘密。
